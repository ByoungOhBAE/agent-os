# AgentOS 지연 진단 및 개선 계획

관측: 2026-09-29 KST. 상태: **실험·진단 완료 / 개선안 초안 / 운영 변경 미승인·미실행**.

## 결론

1. **어댑터 자체가 큰 지연의 원인이라는 증거는 없다.** 같은 Opus 5.5·프로필·입력으로 직접 gateway 호출과 실제 설치 어댑터를 비교했으며 둘 다 약 3초였다.
2. **여러 봇이 무조건 순차 처리되는 구조는 아니다.** 독립 작업 두 개의 gateway 실행은 실제로 겹쳤고, 기존 Paperclip 작업에도 병렬 실행 기록이 있다.
3. **작업 규모 대비 과도한 절차와 검증 범위는 개선 후보다.** 실제 블로그 작업에서는 담당 봇 완료 후 최종 완료까지 25분 35초가 걸렸다. 이를 전부 불필요한 시간으로 단정하지는 않는다.
4. **이전 설명 정정:** HER-11은 단순 제목 5개 요청이 아니라, 사용자가 새 봇 생성·부서 배치·기억 저장도 요청한 작업이다. 그 전체 63분을 제목 생성 시간이라고 비교하면 잘못이다.

## 증거와 범위

- 재현 데이터: [evidence/agentos-latency-20260929.json](evidence/agentos-latency-20260929.json)
- 실험 계획: [agentos-latency-experiment-plan.md](agentos-latency-experiment-plan.md)
- 기존 작업 10개, 연결된 고유 실행 17개를 조회했다. 이슈 실행 목록은 부모의 실행을 자식에도 포함하므로 담당자와 실제 taskId로 분리했다.
- 전체 로그의 바이트 수 일치를 확인했지만, 원문 명령·자격증명·내부 추론은 결과 파일에 저장하지 않았다. 도구 종류·시간·오류 여부와 대략적 분류만 집계했다.
- 이번 실험은 **직접 Hermes gateway ↔ 설치된 Paperclip Hermes 어댑터** 비교다. Paperclip 큐와 비서실장을 포함한 새 end-to-end A/B 실험은 아니다. 운영 비서실장이 다른 요청 두 개를 실행 중이라 실험 업무를 추가하지 않았다.
- 모델은 모든 실험의 Hermes 세션 DB에서 `claude-opus-5-5`, 호출 1회, 도구 호출 0회를 확인했다. 이는 모델의 자기소개가 아니다. 실제 제공사 추론 강도는 별도 노출되지 않아 양쪽에 동일한 `reasoning_effort: high` 요청을 보낸 사실까지만 확인했다.
- `billing_provider=anthropic`, `billing_mode=null`이다. 이번 메타데이터만으로 실제 청구 방식·금액을 확정하지 않는다. 프로필의 제공사 API 키 override는 없었고 다른 모델로 대체하지 않았다.

## 실험 1 — 같은 조건의 전달 경로 비교

고정 조건: 동일 프로필 `pc-2e6cbe27`, 동일 입력·instructions·model·provider·model_options, 새 세션, WSL의 동일 Node 호스트. 세션 ID 외 요청 본문 hash는 6회 모두 일치했다. 실행 순서는 직접 → 어댑터 → 어댑터 → 직접 → 직접 → 어댑터.

과제: 제공된 주문 6건에서 취소 1건을 제외하고 품목별 수량·매출 및 총매출을 계산해 JSON 반환. 기대값은 코드로 검증했다.

| 경로 | 반복 | 전체 소요 범위 | 캐시가 있는 실행 중앙값 |
|---|---:|---:|---:|
| 직접 gateway | 3 | 3.05~3.78초 | 3.28초 (2회) |
| 실제 설치 어댑터 | 3 | 2.94~2.96초 | 2.95초 (3회) |

**실제 봇 설정(`agent.reasoning_effort: max`)으로 재실험**: 같은 프로필·입력·순서, 6/6 정답, 모델 Opus 5.5 확인.

| 경로 | 반복 | 범위 | 중앙값 |
|---|---:|---:|---:|
| 직접 gateway | 3 | 3.81~4.19초 | 4.09초 |
| 실제 설치 어댑터 | 3 | 3.95~5.45초 | 4.11초 |

차이 0.02초로 측정 잡음 범위다. high와 max 모두 어댑터 경로 추가 지연은 초 단위 미만이다.

- 첫 직접 실행만 cache-write 27,796토큰, 이후 5회는 같은 양의 cache-read였다. 출력은 모두 79토큰이었다.
- 6/6 정답, 6/6 도구 0회, 프로필 config/SOUL/MEMORY/USER hash 변경 없음.
- POST 수락은 약 19~45ms. 이는 Paperclip 스케줄러 대기 시간이 아니라 gateway 요청 수락 시간이다.
- **해석:** 수분 단위의 어댑터 지연은 관측되지 않았다. 표본이 작고 제공사 부하·캐시가 통제되지 않아 어댑터가 더 빠르다고 결론 내리지 않는다. 대규모 코딩 작업의 성능비를 이 산술 과제로 일반화하지 않는다.

## 실험 2 — 독립 작업의 순차·동시 실행

두 실제 idle Hermes 프로필(`pc-2e6cbe27`, `pc-7686fab2`)에 같은 과제를 실행했다. 각 프로필은 순차·동시 조건에 모두 등장하며 모델과 과제는 동일하다. 프로필 간 기억·스킬은 같지 않지만 각 프로필의 설정은 조건 간 변경하지 않았다.

| 실행 | 두 작업 모두 끝날 때까지 | 두 요청 실행 구간 겹침 |
|---|---:|---:|
| 순차 1 | 6.00초 | 0초 |
| 동시 1 | 3.40초 | 2.48초 |
| 동시 2 | 3.47초 | 2.52초 |
| 순차 2 | 5.74초 | 0초 |

8/8 정답, 실행 모델 Opus 5.5, 도구 0회, config·기억 원본 변경 없음. 이는 gateway의 실제 동시 실행 증거이며 **비서실장이 자동으로 올바른 병렬 계획을 세운다는 증거는 아니다**.

## 실제 작업 기록 — 어디에서 시간이 쓰였나

### 블로그 제목 + 새 봇/기억 검증 (HER-11, 자식 HER-12)

| 중복 없이 나눈 구간 | 시간 | 의미 |
|---|---:|---|
| 요청 접수 → 승인 카드 생성 | 9분 56초 | 계획·사전 조사 |
| 승인 카드 생성 → 사용자 승인 | 3분 39초 | **사람의 승인 대기: 시스템 성능에서 제외** |
| 승인 → 담당 봇 작업 생성 | 12분 31초 | 요청된 새 봇 생성·배치·준비 포함 |
| 담당 봇 작업 생성 → 완료 | 11분 37초 | 작성·검색·기억 저장·문서 등록 포함 |
| 담당 봇 완료 → 부모 작업 완료 | 25분 35초 | 검증·정리·최종 보고 |
| 합계 | **63분 18초** | 코드로 구간 합계 일치 확인 |

담당 봇 완료 뒤 구간이 전체의 약 40.4%다. 해당 비서실장 실행(`222d8026-cccb-4eb5-aed3-fbde7da064e7`)은 종료 후 정리까지 약 26분 9초, 도구 호출 52회였다.

- 도구: terminal 36, read_file 4, web_extract 1, skill_view 2, write_file 3, patch 5, skill_manage 1.
- 로그 미리보기에서 DB 검사 7회, 자격증명/비밀값 검사 관련 8회, 프로필/기억 관련 16회, 보고 관련 7회로 분류됐다. 분류는 서로 겹치며, 미리보기 기반이므로 정확한 행위 수 또는 불필요한 검사 수가 아니다.
- 제목 개수·길이·근거·기억 저장·새 봇 개수 확인은 승인된 완료 기준에 포함돼 있어 필요하다.
- 반면 여러 프로필과 세션 DB를 반복 조회하고, 보고서를 여러 번 고치며, 매번 새 검증 코드를 구성한 흔적은 **검증 범위를 줄이고 정형화할 후보**다. 신규 봇 생성 실패 정리 같은 예외 처리도 섞여 있어 전부 제거할 수는 없다.
- 도구가 보고한 duration 합은 약 326.7초. 나머지를 곧바로 '모델 추론 시간'으로 부르지 않는다. 모델 대기·생성·도구 사이 간격·전달 지연을 분리할 제공사 시각 정보가 없다.
- Hermes 해당 부모 세션의 API 호출 누계는 93회, 담당 봇 세션은 14회였다(읽기 전용 DB 조회). 세션 누계이지 각 단계의 개별 호출 수가 아니며, 토큰 집계를 실제 비용으로 환산하지 않았다.

### 병렬/의존관계 (HER-6 → HER-7/8/9)

- 스킬 탐색 HER-7 시작: `2026-09-27T04:48:28.318Z`
- 디자인 HER-8 시작: `2026-09-27T04:48:28.415Z` — **0.097초 차이로 병렬 시작**.
- 구현 HER-9의 실제 `blockedBy`는 디자인 HER-8이다. 디자인 완료 `04:54:44.941Z` 뒤 구현 시작 `04:54:45.092Z` — 약 0.151초.
- '시안대로 구현' 과제의 디자인→구현 순서는 타당하다. 이를 무조건 동시에 돌리면 재작업을 늘릴 수 있다.
- 이 옛 실행들은 현재 gateway 실험과 같은 런타임이라고 가정하지 않는다. 역사적 스케줄링 동작을 보여 주는 증거로만 사용한다. 도구 이벤트가 파싱되지 않는 옛 로그는 '도구를 쓰지 않음'이 아니라 **도구 계측 미관측**이다.

### 대기열

조회한 고유 실행 17개의 Paperclip `createdAt → startedAt`은 **0.051~0.085초**였다. 이 표본에서 긴 큐 대기는 보이지 않았다. 이 값에는 선행 작업 차단·사용자 승인·모델 제공사 내부 큐가 포함되지 않는다. 따라서 모든 대기 문제가 없다는 의미는 아니다.

## 현재 지침에서 확인한 구조

현재 비서실장 AGENTS.md는 요청마다 계획 문서 → 승인 카드 → 필요 시 조직/봇 준비 → 하위 작업 → 감독 → 최종 보고를 명시한다. 역할 지침은 약 10,288자이며 작은 표준 작업에 대한 명시적 간소화 분기가 없다.

반면 '순서가 있으면 blockedByIssueIds'라고 쓰여 있으므로 **모든 봇을 직렬화하라는 규칙은 없다**. 이번에 문제로 확인한 것은 전역 직렬화 결함이 아니라, 작업 크기와 위험에 비해 절차·검증 범위가 커질 수 있다는 점이다.

## 개선안 — 아직 승인되지 않은 초안

### P1. 작업 종류에 맞는 경로를 명시

- 사장님은 계속 비서실장 한 곳에만 요청한다. 직접 봇 채팅을 다시 열 필요는 없다.
- 이미 승인된 저위험 표준 작업은 기존 담당 봇 1개를 재사용하고, 추가 조직 조사·봇 생성·장문의 계획 재작성을 하지 않는 경로를 제안한다.
- 새 봇 생성, 외부 발행, 설정·배포·권한 변경은 기존 계획·승인 경로를 유지한다.
- **현재 승인 규칙은 그대로 둔다.** 어떤 표준 작업을 사전 승인된 것으로 볼지는 사용자 결정이 필요하다. 단순히 '빠르게'라는 이유로 승인 카드를 자동 수락하지 않는다.

### P1. 검증을 생략하지 말고 한 번에, 관련 범위만 검사

- 제목 개수·길이·금칙어 등 확정적 검사는 재사용 가능한 한 검사로 묶는다.
- 자식은 결과물과 검사 결과·대상 파일 hash를 전달한다. 비서실장은 결과물과 필요한 독립 검증을 한 번 수행한다.
- 기억 저장 검증은 해당 봇의 변경 항목에 한정한다. 비밀값 검사는 결과물과 이번 변경 대상 중심으로 한 번 수행하고, 누출 신호가 있을 때만 범위를 확장한다.
- 전체 프로필·세션 DB 재검사, 동일 링크 재조회, 보고서 의미 없는 재작성은 실패 신호·변경 사항이 있을 때만 반복한다.
- 스킬 개선처럼 다음 작업을 위한 유지보수는 이번 결과의 정확성에 필요할 때만 완료 경로에 둔다. 시간 제한 때문에 본 작업을 쪼개자는 제안은 아니다.

### P2. 독립 작업만 병렬 배정

- 계획에 실제 입력 의존관계를 표시한다. 선행 산출물을 소비하지 않는 조사·분석은 같이 실행한다.
- 디자인을 보고 구현하는 작업처럼 필요한 순서는 유지한다.
- 서로 다른 파일/읽기 전용이면 병렬 후보, 같은 파일 수정이나 공통 자원 변경이면 격리 또는 명시적 순서가 필요하다.
- 동시 실행 수를 더 높이는 것은 이번 근거로 우선하지 않는다. 현재 설정값 20은 실효 처리량 보장이 아니며, 구독 제한·문맥 충돌도 고려해야 한다.

### P2. 단계별 시간 계측

- 요청 접수, 승인 요청/응답, 담당 배정, 실행 시작/첫 출력, 도구 실행, 결과 등록, 검토 시작/끝, 최종 완료를 분리한다.
- 사람 승인·선행 작업 의존·제공사 대기를 서로 다른 사유로 보여 준다.
- 실행 이벤트가 없는 시간을 모델 추론으로 단정하지 않는다. 캐시 입력과 실제 신규 입력도 구분한다.

## 개선 후 인수 기준·검증 계획

1. 고정된 저위험 과제 묶음을 같은 모델·추론 설정·프로필 스냅샷·출력 품질 기준으로 실행한다. 기존 전체 경로와 개선 전체 경로를 번갈아 최소 3쌍 비교한다.
2. 사용자 승인 대기를 뺀 end-to-end 중앙값을 비교한다. **30% 감소는 제안 목표이지 이번에 달성한 결과가 아니다.** 품질 검사와 필요한 승인 보존이 속도보다 우선이다.
3. 독립 자식 2개는 실제 실행 구간이 겹치고, 의존 작업은 선행 산출물 검증 전에 시작하지 않는다.
4. 자식 완료 후 검증·보고의 호출 수와 소요 시간을 기록한다. 변화 없는 대상의 반복 검사는 사유가 있어야 한다.
5. 새로운 시험은 운영 작업과 분리한다. 실패·재시도·미완료를 숨기지 않고 같은 기준으로 집계한다.
6. 프로필 기억·설정·운영 데이터 보존 및 변경 범위 검증, 필요 시 이전 지침으로 되돌릴 백업을 준비한다.

## 선택하지 않은 방법

- 모든 봇 무조건 병렬: 실제 의존관계·충돌·재작업 위험 때문에 제외.
- 검토/검증 삭제 또는 자동 승인: 품질·사용자 권한을 훼손하므로 제외.
- 모델을 더 싼/빠른 것으로 변경: 사용자가 Opus 5.5 동일 조건을 지정했으므로 제외.
- 운영 비서실장에 추가 실험 요청을 넣거나 현재 작업 중단: 비교 조건과 운영 안전을 해치므로 제외.
- 산술 실험만으로 전체 AgentOS가 빠르다고 주장: 배정·보고를 측정하지 못하므로 제외.

## 정정 (같은 날 추가 관측) — 앞 실험은 계획 단계를 측정하지 못했다

앞 실험은 도구 0회·문맥 약 2.8만 토큰·3초짜리 계산이라 비서실장의 실제 계획 단계를 대표하지 못한다. 실행 중인 요청 2건(읽기 전용 관측):

| 요청 | 경과 | 단계 | 모델 호출 | 호출당 문맥(캐시 읽기/호출) | 출력 토큰 | 도구 실행 합 | 도구 사이 대기 합 |
|---|---:|---|---:|---:|---:|---:|---:|
| HER-20 피그마 커넥터 설치 | 58분 | 계획 전(계획 문서·승인 카드 없음) | 81 | 약 14.6만 | 316,924 | 약 4.7분 | 52.9분 |
| HER-21 조직도 봇 배치 | 53분 | 계획 전 | 60 | 약 14.1만 | 290,873 | 약 4.1분 | 49.3분 |

- 시간의 약 90%가 도구 실행이 아니라 **모델 응답 대기**다. 출력 토큰/대기 시간 ≈ 초당 100토큰으로, 대부분 생성(주로 추론) 시간으로 보인다. 추론/본문 비율은 노출되지 않아 확정하지 않는다.
- 계획 문서를 쓰기 전에 Paperclip 서버 빌드 파일·Hermes 소스·로그를 수십 번 조사하고 있다. 지침의 1단계 "계획"에 **조사 범위·시간 상한이 없다**.
- 두 요청 모두 승인 필요 작업(설치·조직 변경)이라 "바로 처리" 분류로는 빨라지지 않는다. 별도 대책이 필요하다: 계획 전 조사 상한, 미확인 사항은 가정으로 적고 승인 후 조사, 계획 단계 추론 강도 조정(측정 후 결정).

## 실행 상태와 다음 단계

- 관측 완료: 동일 입력 어댑터 비교 6회, 두 프로필 순차/동시 8회, 실제 작업 기록 분석.
- 아직 미관측: 현재 전체 비서실장 경로 대 직접 처리의 통제된 end-to-end 비교, 제공사 내부 순수 추론 시간, 개선 후 절감률, 청구 금액.
- 운영 절차·봇 설정·기억 파일·실행 중 작업은 변경하지 않았다. 실험 세션/사용량 기록은 14회 추가됐다.
- 권장 후속 방식: **한 담당자가 간소화 경로와 검증 규칙을 함께 수정하는 제한된 변경**. 같은 지침·승인 정책이 얽혀 있어 지금은 여러 구현 봇으로 나누는 것보다 적합하다.
- 이 문서의 계획 수락과 실제 구현 승인은 별개다. 사용자에게 간소화 대상과 승인 경계를 확인한 뒤 명시적인 실행 지시를 받아야 한다.
