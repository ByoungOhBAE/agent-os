# 계획(초안): 비서실장 "조금 복잡한 요청" 처리 과정 분석

상태: **초안, 승인 전.** 분석만 하며, 비서실장 지침·봇 설정은 바꾸지 않는다.

## 목표
1. 비서실장이 복잡한 요청 하나를 받아 끝낼 때까지 거치는 단계를 실제 기록으로 나누고, 단계마다 걸린 시간·토큰·도구 호출을 잰다.
2. 각 조사 행동을 "비서실장이 꼭 해야 함 / 담당 봇이 어차피 다시 함(중복) / 아무도 필요 없음"으로 분류해 낭비량을 숫자로 낸다.
3. 필요 없는 단계, 잘못된 분배, 지침의 문제점을 근거(run ID·시각)와 함께 목록으로 만든다.
4. 고칠 방안 후보와, 적용 전후를 같은 조건으로 비교하는 방법을 제시한다.

비서실장의 목표 정의(사장님): **요청을 받으면 목표에 맞는 계획, 업무 배분(없으면 봇 생성)을 정확하고 빠르게.** 구현 수준의 조사는 담당 봇 몫.

## 비목표
- 지침·설정·스킬 수정은 하지 않는다(분석 결과 승인 후 별도 작업).
- Paperclip·Hermes 본체 수정, 모델 변경은 하지 않는다.
- 진행 중인 HER-21을 멈추거나 건드리지 않는다(읽기 전용 관측).

## 이미 확인된 사실 (2026-09-29 조회)
| 이슈 | 내용 | 비서실장 첫 실행(계획까지) | 이후 실행 | 결과 |
|---|---|---:|---|---|
| HER-20 | 피그마 MCP 봇 로그인 | 85.1분 | 감독 14.6분 | 완료, 하위 작업 없음(비서실장이 직접 처리한 것으로 보임) |
| HER-21 | 조직도 검수봇 | 107.1분 | 7.1분 + 진행 중 | 하위 HER-22, HER-23 |
- 두 요청 모두 추론 강도 '최대'로 시작(이후 11개 봇 '높음'으로 변경, `e03276c`).
- 하위 작업에서 **취소된 실행 4건**: HER-22는 시험_연결확인→검수→시험_연결확인→검수(취소 3회 뒤 성공), HER-23은 코드구현 봇 7.8분 실행 후 취소 → 검수 봇. 배정을 바꾼 흔적으로 보이며 원인은 미확인.
- 같은 계획 과제 실험에서 '높음'은 60~75초, 도구 8~9회로 충분한 계획을 썼다(`eb678d5`). 즉 계획 자체에 긴 조사가 필수는 아니다.
- 지침 흐름(`scripts/setup-chief-single-window.mjs`): 계획 → 승인 카드 → 조직 → 지시 → 감독 → 최종 보고. 계획 문서 필수 항목 9개, **조사 범위·시간 상한 없음.**

## 분석 대상
- 주: HER-20, HER-21(최대 강도, 복잡한 요청), 하위 HER-22, HER-23.
- 비교: HER-11, HER-12(과거 복잡 요청). HER-21이 끝나면 전체를 포함.
- 대조: '높음' 전환 후 들어오는 첫 복잡 요청 1건(있으면).

## 분석 방법
1. **타임라인 추출** (읽기 전용 스크립트 `scripts/chief-process-audit.py`)
   - 출처: `/heartbeat-runs/<id>/log`, 이슈 댓글·문서·interaction 기록, 비서실장 프로필 `state.db`(메시지·도구 호출·토큰).
   - 도구 호출마다 시각, 도구 이름, 대상(파일 경로/API/명령)을 기록. 비밀값은 마스킹, 원시 로그는 저장소에 넣지 않는다.
2. **단계 태깅** — 각 호출을 단계로 분류: 요청 이해 / 조직·봇 목록 확인 / 기술 조사 / 계획 작성 / 승인 대기 / 봇 생성 / 하위 작업 지시 / 감독·재배정 / 검증 / 보고.
3. **필요성 판정** — 조사 행동마다:
   - A. 비서실장 필수(목표·범위·담당 결정에 필요)
   - B. 중복(담당 봇이 작업 중 다시 읽음 — 하위 작업 로그와 같은 파일·명령을 대조해 자동 판정)
   - C. 불필요(결과가 계획·배정에 반영되지 않음 — 계획 문서에 인용 안 된 조사)
   판정 규칙을 먼저 문서로 고정하고, 애매한 건 "판정 보류"로 남긴다.
4. **분배 점검** — 봇 선택이 맞았는지, 재배정·취소 원인(HER-22·23), 봇 생성이 필요했는지, 비서실장이 직접 실행한 일(HER-20)이 봇 몫이었는지.
5. **지침 비판** — 단계별로 "이 단계가 목표(정확·빠른 계획/배분)에 기여하는가"를 근거와 함께 평가. 후보 쟁점:
   - 계획 전 조사 상한 없음 → 구현 수준 조사를 비서실장이 대신함
   - 계획서 9개 항목이 단순 요청에도 무거운지
   - 감독 단계 재깨움(14.6분, 7.1분)에서 하위 결과를 다시 검증하는지 → 검수 봇과 중복
   - 최종 보고 전 재검증 중복
   - 호출당 약 14만 토큰 문맥(지침·스킬·기억 크기)이 적정한지
6. **결과 정리** — 단계별 시간·토큰 표, 낭비 비율(B+C), 쟁점마다 근거 run ID, 개선 후보와 예상 효과.

## 완료 기준
1. HER-20, HER-21의 모든 비서실장 실행이 단계별 시간·토큰·도구 호출 수로 표에 나온다(합계가 실제 실행 시간과 5% 이내 일치).
2. 모든 조사 행동이 A/B/C/보류로 분류되고, B·C 비율이 숫자로 나온다.
3. 취소된 하위 실행 4건 각각의 원인이 기록으로 확인되거나 "확인 불가"로 명시된다.
4. 지침 쟁점마다 근거(run ID, 시각, 도구 호출)가 붙는다. 근거 없는 주장은 없다.
5. 개선 후보마다 "무엇을 바꾸는지 / 기대 효과 / 비교 방법"이 있다.

## 검증 방법
- 단계 합계를 run의 시작·종료 시각과 대조(기준 1).
- 분류 판정 규칙을 표본 10건에 사람이 직접 적용해 스크립트 판정과 비교.
- 개선안 효과는 적용 후 **같은 종류의 실제 복잡 요청**을 '높음'에서 전후 비교(장난감 과제 금지). 실험 봇(pc-2e6cbe27)에 비서실장 지침 사본을 넣어 같은 요청을 재생하는 방식도 검토.
- 저장소 커밋 전 비밀값 grep.

## 위험과 대응
- 로그가 잘리거나 세션 DB에 도구 인자가 없으면 → 판정을 "보류"로 두고 비율 계산에서 따로 표시.
- '최대' 강도 기록만으로는 '높음'에서의 낭비를 과대평가할 수 있음 → 강도별로 나눠 보고, 대조 요청 결과를 기다린다.
- HER-21 진행 중 → 끝난 뒤 최종 수치 확정.

## 선택하지 않은 방법
- 지침부터 바로 고치기: 원인 측정 없이 고치면 "사후 보고가 원인"이라고 잘못 결론 낸 이전 실수를 반복할 수 있다.
- 장난감 요청으로 재현: 실제 조사 행동이 나오지 않아 측정 의미가 없다.
