## 작업 A — AgentOS 전체 점검 3회 + 환각 검수 + 보고서

### A-1. 목표 / 비목표

- **목표**: 지시 충돌, 스킬·하네스 상태, 봇 분류 적절성 등을 근거(파일:줄, 명령 출력, Paperclip 기록) 기반으로 찾아내고, 각 발견을 독립 검증해 “확인/반박/근거 없음”으로 판정한 보고서.
- **비목표**: 점검 중 운영 설정 변경, 봇 고용·해고, 봇 기억 수정, SOUL·스킬 직접 수정. 수정은 보고서 승인 후 별도 작업.

### A-2. 점검 항목

| # | 영역 | 무엇을 보나 | 방법 |
|---|---|---|---|
| 1 | **지시 충돌** | 층별 지시: Paperclip AGENTS.md → 생성된 SOUL.md(비서실장 관리 블록 포함) → auto_load(agentos-common/project/bot) → 로컬 스킬 ~80 → omh-* 120 → 가드 규칙 → MEMORY/USER.md → 작업 폴더의 AGENTS.md/CLAUDE.md/.claude/skills | 규칙 문장 추출 → 같은 주제끼리 묶어 상충·중복·낡은 경로 판정. 같은 트리거를 가진 스킬 겹침(예: plan/ralplan/ulw-plan), 로컬이 외부 스킬 이름을 가리는 충돌, SOUL과 반대되는 스킬 |
| 2 | **스킬·하네스** | 봇별 스킬 목록 차이, auto_load, disabled, external_dirs, 모델·추론 강도, terminal.cwd, 가드 모드, 메모리 용량, 지식 drift, 게이트웨이 상태 | `config.yaml`·디스크 대조, `memory-knowledge check/status`, `hermes-bots.mjs verify all`, 기존 게이트 재실행 |
| 3 | **봇 분류 적절성** | 프로젝트별 담당 봇 유무, 실제 업무량, 역할 중복/공백 | Paperclip 이슈 이력(봇별 배정·완료·반려 수, 마지막 실행), 프로젝트×봇 표. 예상 쟁점: rimbus 봇이 Paperclip 조직에 없음, academy 코드 담당 봇 없음, 블로그 제목/본문 분리 필요성, 시험·스모크 봇 정리 |

| 5 | (추가) **운영 안정성·비용** | 게이트웨이 exit 75, 실행 시간, 실패/재시도, 회수 안 된 실행 | 게이트웨이 진단 로그, Paperclip 실행 기록 |
| 6 | (추가) **보안 노출** | 공개 저장소(agent-os)에 비밀값·내부 주소 유출 | 저장소 전체 패턴 스캔(값은 출력 안 함) |

### A-3. 환각·착각·거짓말 검수 방식

모든 발견은 한 줄씩 `findings.jsonl`에 남긴다: `{id, 주장, 근거 명령/파일:줄, 출력 요약, 판정}`.

- **검수자는 발견자와 분리**: 별도 서브에이전트가 주장만 받고(결론 이유는 안 받음) 근거를 처음부터 다시 실행해 `확인 / 반박 / 근거 없음 / 재현 불가`로 판정.
- **환각 유형 체크**: 존재하지 않는 파일·설정·봇 이름, 실행하지 않은 명령의 결과 주장, 숫자 불일치, 이전 회차 결론 베끼기.
- 점검 대상(봇들)에 점검을 맡기지 않는다 — 자기 감사가 되기 때문.
- 회차별 지표: 발견 수, 확인율, 반박·근거없음 건수와 사례.

### A-4. 3회 진행 구조 (권장안)

| 회차 | 내용 | 특징 |
|---|---|---|
| 1회 | 전 항목 점검 + 독립 검수 | 기준선. 발견 목록 작성 |
| 2회 | **이전 결과를 보지 않은** 새 점검자로 처음부터 다시 + 독립 검수 → 1회와 대조 | 1회에서 놓친 것/1회의 환각을 잡는 용도 |
| 3회 | 두 회차 차이 항목 집중 재조사 + (결정 2에 따라) 승인된 수정 후 재점검 | 최종 확정. 남은 불일치는 “미확정”으로 명시 |

### A-5. 산출물

- `docs/audit/2026-10-agentos/round{1,2,3}/findings.jsonl` + 회차별 요약
- 최종 보고서 `docs/audit/2026-10-agentos/보고서.md`: 한눈에 표 → 영역별 발견(확인된 것만 본문, 반박·근거없음은 별표) → 봇 조직 개편안(제안, 미승인) → 수정 우선순위 → 회차별 검수 통계
- 커밋·푸시(공개 저장소이므로 push 전 비밀값 검사)

### A-6. 완료 기준

- 3회차 모두 findings + 검수 판정 존재, 최종 보고서의 모든 “확인” 항목에 재현 가능한 근거 첨부
- 회차 간 불일치 0건 또는 미확정으로 명시
- 점검 전후 운영 상태 동일(프로필 config/SOUL/MEMORY 해시, Paperclip 봇 수·상태 대조)

## 작업 B — 관제센터 사례 조사 + 개선 샘플 구현

### B-1. 목표 / 비목표

- **목표**: 다른 사람들이 쓰는 AI 에이전트 관제 대시보드 기능을 조사해 AgentOS에 맞는 개선안을 고르고, 디자인→코드까지 **실제 데이터로 돌아가는 샘플**을 보여준다.
- **비목표**: 운영 배포. 샘플은 미리보기 브랜치에서만 만들고, 배포는 샘플을 본 뒤 별도 결정.

### B-2. 단계

1. **조사** (YouTube·블로그·GitHub·제품 문서): AI 에이전트 관제/관측 도구(예: 에이전트 운영 대시보드, LLM 추적·비용 도구, 멀티에이전트 오케스트레이션 UI, Paperclip 커뮤니티 사례). 기능별 표(기능 · 어디서 봤나(링크) · 사용자가 얻는 것 · AgentOS 적용성 · 난이도). 출처 없는 기능은 표에 넣지 않음.
2. **스킬 탐색·설치**: find-skills로 디자인·대시보드·차트 관련 스킬 검색 → 설치 전 SKILL.md를 고정 커밋으로 읽고 위험(바이너리 다운로드 등) 확인 → Hermes(내 쪽)에 설치. 봇에 설치는 이번 범위 밖.
3. **개선안 선정**: 작업 A 결과(예: 봇 상태·환각 검수 지표)와 조사 결과를 합쳐 후보 6~10개 → 사용자가 3~5개 선택. 후보 가설: 봇별 비용·토큰·실행시간 패널, 실행 타임라인/추적 보기, 봇 상태·하트비트 보드, 승인 대기함, 작업별 근거 점수(환각 검수 결과), 실시간 활동 피드, 이상 알림.
4. **디자인 시안**: 현재 화면 스크린샷 진단 → 시안(디자인 스킬 규칙 인용) → `docs/plans/<topic>-시안.md`.
5. **구현 샘플**: git worktree `preview/agentos-control-center` 브랜치, `preview-dist/`로 빌드(운영 `dist` 건드리지 않음), Playwright로 운영 3100에 번들만 바꿔 실제 데이터로 표시.
6. **검증**: tsc·vitest·빌드, 390/768/1440 스크린샷 직접 확인, 운영 번들 해시가 작업 전과 같은지 게이트, 실제 데이터로 못 보여주는 상태는 `[예시]` 표시.

### B-3. 산출물

- 조사 보고서 `docs/research/관제센터-사례조사.md`(링크 포함)
- 설치한 스킬 목록과 검토 기록
- 미리보기 브랜치 push, 전/후 비교 이미지, `GATES-control-center-preview.md`

### B-4. 완료 기준

- 선택된 기능 각각이 실제 데이터로 화면에 표시되고 3개 폭 스크린샷 존재
- 운영 화면 변경 0(served bundle 해시 동일), main 브랜치 무변경
- 조사표의 모든 기능에 출처 링크

## 진행 순서와 규모

1. A 1회 → A 2회 → (B-1 조사는 A와 병행 가능) → A 3회 → A 보고서
2. B 스킬 탐색 → 후보 선정(사용자 선택) → 시안 → 샘플 구현 → 검증
- 예상 시간: A 회차당 2~4시간(서브에이전트 병렬), B 조사 2~3시간, 구현 회차당 3~6시간. 실행 시간 제한 때문에 쪼개지 않고 내용 단위로만 나눈다.

## 위험

| 위험 | 대응 |
|---|---|
| 점검 에이전트 자신의 환각 | 발견자/검수자 분리, 근거 명령 재실행, 회차 간 블라인드 |
| 점검이 운영을 건드림 | 읽기 전용 명령만, 전후 해시 대조 |
| 봇 실제 실행 시 비용·게이트웨이 exit 75 | 실제 봇 턴은 최소화, 실행 시 stall 샘플러 가동 |
| 외부 스킬의 악성·과잉 동작 | 설치 전 고정 커밋 검토, 실행형은 참고 전용 |
| 샘플이 운영에 새어 나감 | worktree + preview-dist + 번들 해시 게이트 |

## 기각한 안

- **봇들에게 자체 점검을 맡기기**: 자기 감사라 환각 검수가 성립하지 않음.
- **3회를 같은 점검자가 반복**: 같은 착각을 반복할 가능성이 큼 → 2회차는 블라인드.
- **샘플을 바로 운영 배포**: 사용자가 보고 결정하는 “시안 먼저” 원칙과 충돌.
